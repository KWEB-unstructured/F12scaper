# 형씨 (게임 로직·스토리 리드) — Claude Code 작업 프롬프트

**쓰는 법**: 레포 루트에서 Claude Code 를 열고, 해당 주차의 코드 블록을 통째로 붙여 넣는다.
CLAUDE.md 는 자동으로 읽히므로 규칙은 다시 설명하지 않아도 된다.
작업 전에 브랜치를 만든다: `git switch -c 형씨/<작업명>`

담당 파일: `src/core/game.js` `state.js` `hash.js` `rules.js`, `src/content/`, `src/stages/stage3.js` `stage4.js` `stage7.js` `types.js`, `public/stages/`, `scripts/`
그리고 모든 단계의 **대사·힌트 문구**(파일은 각 담당자 것이어도 문구 최종 결정은 형씨)

## 1주차 — 스토리·단계별 정답 확정, 단계 모듈 형식 확정, 3단계

```
나는 이 프로젝트에서 게임 로직·스토리 담당(형씨)이야. 이번 주 목표는 스토리와 단계별 정답 확정, 단계 모듈 형식 확정, 3단계 구현이야.

먼저 읽어 줘: CLAUDE.md, docs/spec.md, docs/contracts.md, src/stages/types.js, src/stages/stage1.js, src/stages/stage3.js, src/core/game.js, src/core/state.js, src/content/story.js

할 일
1. 단계 모듈 형식 검토: docs/contracts.md 1절과 src/stages/types.js 의 형식으로 1~8단계를 모두 만들 수 있는지 검토해 줘.
   특히 4단계(새로고침이 퍼즐의 일부), 5단계(fetch 결과로 단서), 7단계(외부 스크립트 로드), 8단계(서버 검증)를 하나씩 대입해 보고,
   부족한 필드나 ctx 기능이 있으면 변경안을 제안해 줘. 내가 승인하면 types.js 와 contracts.md 를 같이 고친다.
2. 스토리 문서: docs/story.md 를 새로 만들어 줘.
   - 신입 전산 조교(플레이어), 선배 조교(안내자), 유령 관리자의 말투 설정
   - 1~8단계 각각: 선배 조교 시작 대사 1~2줄, 클리어 후 유령 관리자 도발 1줄, 오답 도발 2~3개
   - 유령 관리자 정체 공개(8단계 클리어) 장면 초안 — 정체 아이디어 3개를 제안하고 내가 고른다
   - 튜토리얼(1~3)은 열어야 할 탭을 대사로 직접 알려 주고, 4단계부터는 알려 주지 않는다
3. 정답·조각 설계: 각 단계의 조각(정답)과 8단계 조합 규칙 후보를 2~3개 제안해 줘.
   - 조각은 짧은 영문 소문자/숫자 단어 권장 (normalize 가 소문자화함)
   - 8단계 조합 규칙은 "지금까지 모은 것을 정리하는" 수준으로, 새 개발자 도구 기능을 요구하지 않는다
   - 정답 원문은 레포에 커밋하지 않는다. 확정본은 팀 채팅에 공유하고, 레포에는 해시만 넣는다. 최종 정답은 김씨에게 FINAL_ANSWER 환경변수로 전달한다.
4. src/content/story.js 를 docs/story.md 내용으로 갱신(인트로, 기본 도발, 힌트 권유 문구).
5. 3단계(src/stages/stage3.js): 지금 예시 구조(window.unlock, 정리 함수)를 유지하고 퍼즐을 완성해 줘.
   - 열쇠는 페이지 제목(document.title)에 숨긴다. 탭 제목에서 바로 읽히지 않게 살짝 꼬아도 되지만 튜토리얼 난이도(★★)를 넘지 않게.
   - 콘솔 로그로 unlock() 의 존재를 알린다. 틀린 열쇠면 유령 관리자 경고를 콘솔에 남긴다.
   - 힌트 3개 작성.

완료 기준
- docs/story.md 초안과 정답·조합 규칙 후보가 나왔고, 내가 고를 수 있게 선택지로 정리돼 있다.
- 3단계를 콘솔만으로 풀 수 있다. 다음 단계로 넘어가면 window.unlock 이 사라지고 title 이 돌아온다.
- npm run build 통과. 담당 외 파일은 수정하지 않는다.
```

## 2주차 — 4·7단계, 진행 저장, 해시 비교

```
나는 게임 로직·스토리 담당(형씨)이야. 이번 주는 4·7단계와 진행 저장·해시 비교 마무리야.

먼저 읽어 줘: CLAUDE.md, docs/contracts.md, docs/story.md, src/core/state.js, src/core/hash.js, src/core/game.js, src/stages/stage4.js, src/stages/stage7.js, public/stages/stage7-flash.js

할 일
1. 4단계(src/stages/stage4.js): "권한이 없습니다" 화면.
   - mount 시 role 쿠키가 없으면 document.cookie 로 role=student 를 심는다 (path=/, HttpOnly 불가하게 클라이언트에서).
   - role=admin 이면 조각을 보여 준다. 플레이어가 Application > Cookies 에서 값을 바꾸고 새로고침하는 흐름.
   - 새로고침해도 진행이 4단계로 이어지는지 확인 (진행 저장은 localStorage).
   - resetProgress() 가 role 쿠키도 지우는지 확인.
2. 7단계(src/stages/stage7.js + public/stages/stage7-flash.js): 정답이 0.1초만 깜빡이는 보스 단계.
   - 플레이어가 Sources 에서 stage7-flash.js 를 열고, 정답이 변수에 담기는 줄에 중단점을 걸어 값을 잡는다.
   - stage7-flash.js 는 번들되지 않는 일반 스크립트다. 변수명·줄 구성을 사람이 읽기 좋게 쓰고, 정답 원문을 문자열 리터럴로 그대로 두지 말고 실행 중에 계산되게 해서 "코드만 읽어서는" 바로 안 보이게 한다 (그래도 컴공 학생이 코드를 따라가면 알아낼 수 있는 수준).
   - stage7.js 의 mount 에서 <script src="/stages/stage7-flash.js"> 를 붙이고, 정리 함수에서 스크립트와 타이머를 정리한다. 반복해서 깜빡이게 해 중단점을 걸 기회를 여러 번 준다.
   - 깜빡이는 효과는 광과민성 배려로 강한 번쩍임·빠른 색 반전을 피한다.
   - 힌트 3개: 힌트 3을 다 쓰면 누구나 풀 수 있어야 한다 (어느 파일, 몇째 줄, 무엇을 보는지까지).
3. 진행 저장·해시 점검
   - src/core/state.js: localStorage 값이 깨졌거나 예전 형식일 때 앱이 죽지 않게 방어 (형식 버전 필드 추가 검토).
   - src/core/hash.js, scripts/hash.mjs: 브라우저와 Node 결과가 같은지 확인하는 간단한 테스트 스크립트를 scripts/ 에 추가.
   - src/core/game.js 의 규칙(5회 오답 시 힌트 권유, 힌트 누적 감점 3/5/10분)이 기획과 맞는지 확인.

완료 기준
- 4단계: 쿠키 수정 + 새로고침만으로 풀린다. 7단계: 중단점으로 풀린다. 둘 다 임시 정답 대신 확정 정답의 해시로 바뀌어 있다(확정됐으면).
- 3→4→…→7 단계 전환 때 이전 단계의 전역 함수·타이머·스크립트가 남지 않는다.
- npm run build 통과. 담당 외 파일은 수정하지 않는다.
```

## 3주차 — 힌트 3단계 문구·감점, 전체 단계 연결, 내부 테스트

```
나는 게임 로직·스토리 담당(형씨)이야. 이번 주는 전체 힌트 문구 확정, 1~8단계 연결 점검, 내부 테스트 준비야.

먼저 읽어 줘: CLAUDE.md, docs/spec.md, docs/story.md, src/stages/*.js 전부, src/core/game.js, src/screens/stage.js(읽기만)

할 일
1. 힌트 문구 전수 점검: 1~8단계 hints 를 표로 뽑아서 기준에 맞는지 검토해 줘.
   - 힌트 1: 방향만 ("쿠키는 어디에 저장될까?") / 힌트 2: 열어야 할 탭과 위치 / 힌트 3: 거의 정답 수준
   - 선배 조교 말투 통일, 크롬 기준 메뉴 이름(Elements, Console, Application, Network, Sources, 기기 툴바) 정확히
   - 수정안을 표로 보여 주고, 내가 승인하면 각 단계 파일의 hints/guide/taunts 문구만 고친다 (다른 담당자 파일은 문구 필드만 수정, 로직은 건드리지 않음).
2. 전체 연결 점검: 1~8단계를 처음부터 끝까지 진행하는 체크리스트(docs/playtest-checklist.md)를 만들어 줘.
   - 단계별: 시작 대사 → 퍼즐 → 단서 → 정답 → 유령 관리자 도발 → 복구율 증가 순서가 지켜지는지
   - 새로고침·"처음부터 다시"·브라우저 재시작 후 이어하기
   - 단계 전환 시 남는 전역 상태(window 함수, document.title, 쿠키, 타이머)
3. 내부 테스트 운영 문서(docs/playtest-plan.md): 기획서 테스트 계획 기준으로
   - 테스터 6명(개발자 도구 초보 3, 컴공 3) 관찰 기록표: 단계별 소요 시간, 막힌 지점, 사용 힌트, 혼잣말 메모
   - 판정 기준: 한 단계 10분 이상 막힘 → 힌트 수정, 1분 안에 풀림 → 퍼즐 강화
   - 진행자가 개입하지 않는 규칙
4. 교차 테스트: 다른 팀원이 만든 단계(1·2·5·6·8)를 힌트 없이 푸는 관점에서 막힐 지점을 짚어 줘.

완료 기준
- 체크리스트대로 1~8단계를 끝까지 통과(김씨 API 가 아직이면 mock 으로).
- 힌트 문구 수정은 승인받은 것만 반영. npm run build 통과.
```
